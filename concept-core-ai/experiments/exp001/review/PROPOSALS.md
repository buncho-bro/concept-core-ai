# PROPOSALS

以下は仕様改善案であり、すべて **PROPOSED / 未承認** である。

## P-01 ラベル漏洩をインターフェースとテストで防止する

- 理由: 「使ってはならない」という記述だけでは、同じ batch 辞書に評価ラベルが含まれる実装などの偶発的漏洩を検出しにくい。
- 改善案: 学習用 Dataset/DataLoader は画像と `sample_id` だけを返し、評価メタデータは解析モジュールだけが別ファイルから結合する。自動テストで loss 計算経路に `color`/`shape` が渡らないことを確認する。
- 利点: 研究原則をコード構造で強制でき、監査しやすい。
- 欠点: Dataset 実装と解析実装が分かれ、コード量が少し増える。
- 代替案: 同じレコードを使いつつ学習時にラベル列を明示的に drop し、実行時 assertion を置く。

## P-02 乱数を用途別に記録する

- 理由: 単一の `seed` では、画像生成、split、モデル初期化、DataLoader、probe の乱数を独立に再現・比較できない。
- 改善案: master seed と、そこから決定的に導出した `generation_seed`、`split_seed`、`model_seed`、`loader_seed`、`probe_seed` を保存する。
- 利点: どの乱数要因で結果が変わったかを切り分けられる。
- 欠点: 設定項目が増え、seed 管理が複雑になる。
- 代替案: 全処理に単一 seed を使い、処理順も固定・記録する。ただしモジュール追加で乱数列が変わりやすい。

## P-03 全 split の latent と Encoder 状態を明示する

- 理由: probe の適切な学習には Train/Validation latent が必要で、未学習モデルにも「同じ解析」を行うには初期・最終状態の区別が必要である。
- 改善案: `encoder_state` と `split` 列を持つ単一ファイル、または `latent_vectors/{initial,final}/{train,validation,test}.csv` を成果物として定義する。
- 利点: 解析の入力が完全に残り、probe と未学習比較を再実行できる。
- 欠点: 保存容量とファイル数が増える。
- 代替案: checkpoint と dataset metadata だけを保存し、解析時に latent を毎回再抽出する。再抽出の決定性検証が別途必要になる。

## P-04 未学習・学習済み比較の成果物名を対称にする

- 理由: 現行の PCA、距離、latent の成果物名は学習済みモデル用に一組しかなく、Section 13 の未学習モデルへの「同じ解析」を保存できない。
- 改善案: `analysis/initial/` と `analysis/final/` に同一形式の PCA、距離、probe 結果を保存し、比較要約を別ファイルに置く。
- 利点: 比較対象の取り違えを防ぎ、差分を機械的に集計できる。
- 欠点: 例示された成果物構成から変更される。
- 代替案: 各ファイル名に `_initial` / `_final` suffix を付ける。

## P-05 評価結果に不確実性と基準精度を含める

- 理由: accuracy の一点値と平均距離だけでは、有限サンプルや seed 差を評価できない。
- 改善案: クラス別件数、balanced accuracy、confusion matrix、chance level、seed 間の分布、事前に選んだ信頼区間または効果量を保存する。
- 利点: 「差がある」ことと「差が安定している」ことを区別できる。
- 欠点: 統計手法の選定と説明が必要になり、報告が複雑になる。
- 代替案: 各 seed の raw 指標だけを全件保存し、統計的結論は Experiment 002 へ回す。

## P-06 再構成品質の成果物を定義する

- 理由: `report.md` は再構成結果を要求するが、Test reconstruction loss や入力・出力比較画像の保存先が定義されていない。
- 改善案: Train/Validation/Test の再構成損失と、固定 `sample_id` の `reconstruction_grid.png` を成果物に追加する。
- 利点: 潜在解析を、そもそも再構成を学習できたかと切り分けて解釈できる。
- 欠点: 可視化サンプルの選び方を事前に固定する必要がある。
- 代替案: 数値損失のみを保存する。または全 Test 再構成を保存するが、容量が増える。

## P-07 実行環境とデータ完全性を記録する

- 理由: `git_commit` と設定だけでは、ライブラリ、ハードウェア、決定性設定、生成データの差を追跡できない。
- 改善案: Python/主要ライブラリ/OS/device のバージョン、決定性設定、設定・metadata・checkpoint のハッシュを manifest に保存する。
- 利点: 再現不能時の原因を特定しやすい。
- 欠点: 環境情報が増え、異なる device での完全一致を保証するものではない。
- 代替案: lockfile と `git_commit` のみ保存し、ハッシュは省略する。

## P-08 実行後に設定を書き換えない

- 理由: Section 18.1 の「実験開始後に設定値が変更された場合、実際に使用された値を保存」は、開始時設定の上書きと解釈でき、途中変更の履歴が失われる可能性がある。
- 改善案: 実行開始時に解決済み設定を immutable に保存し、途中変更が必要なら run を失敗として残して新しい run を開始する。実行時派生値は別の manifest に記録する。
- 利点: 実際にどの条件で処理したかが追跡でき、失敗 run も保存される。
- 欠点: 軽微な設定ミスでも run 数が増える。
- 代替案: `config_initial.yaml` と `config_effective.yaml` の両方を保存し、変更履歴をログに残す。

## P-09 解析計画とハイパーパラメータ探索規則を最初の run 前に固定する

- 理由: 結果を見た後に PCA 表示、距離尺度、probe 設定、checkpoint を選ぶと、良く見える結果だけを採用できてしまう。
- 改善案: 主解析・補助解析・探索解析を区別し、主解析の設定と選択規則を `spec.md` に事前登録する。
- 利点: 過大解釈と選択バイアスを抑えられる。
- 欠点: 初回実験で有用な探索が制限される。
- 代替案: Experiment 001 を探索専用にし、得られた仮説を事前登録した Experiment 002 で検証する。
