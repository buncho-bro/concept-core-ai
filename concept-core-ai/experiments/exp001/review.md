# Experiment 001 仕様レビュー

- 対象: `experiments/exp001/spec.md`
- レビュー日: 2026-09-22
- 状態: **REVIEW / 未承認**

この文書は仕様そのものではない。以下の提案はすべて **PROPOSED** であり、人間による決定と `spec.md` への反映が行われるまで、承認済みの研究条件として扱わない。

## BLOCKERS

### B-01 成功条件を操作的に判定できない

- 人間の判断が必要な項目: 「再現可能な規則的構造」を、どの指標、比較対象、効果量、反復数で成立とみなすか。実行前に seed 数と成功判定手順を固定する必要がある。
- 理由: PCA の見た目、線形プローブ精度、距離差のどれを優先するかが未定であり、現在の記述だけでは同じ結果に対して成功・失敗の両方を主張できる。成功条件は Human の承認事項でもある。
- PROPOSED: 主判定指標、未学習モデルとの差、複数 seed における集約方法を事前登録し、PCA は補助資料に限定する。
- 利点: 結果を見た後の基準選択を防ぎ、成功判定を再現できる。
- 欠点: seed 数と統計基準を増やすほど計算量が増え、探索的な観察の自由度は下がる。
- 代替案: Experiment 001 を「判定を伴わない探索実験」と明記し、成功条件を削除して観測結果のみ報告する。ただし、現行の「成功条件」とは両立しない。

### B-02 データ生成条件が確定していない

- 人間の判断が必要な項目: RGB 基準値と変動方法、位置・大きさ・回転の範囲と分布、図形の塗り方、境界のアンチエイリアス、座標と size の定義、画面外クリッピングの可否。
- 理由: これらはデータセット条件であり、色・形の読み出しやすさを直接変える。設定可能であることだけでは、初回 run の条件は決まらない。
- PROPOSED: すべての分布を数値と単位で `spec.md` に固定し、全図形が画像内に収まる制約を設ける。三角形と四角形の回転分布も個別に明記する。
- 利点: データセットを独立に再生成でき、交絡要因を説明しやすい。
- 欠点: 人工世界の設計に人間の選択が増え、その選択への依存性が残る。
- 代替案: 変動なしの基準 run と変動ありの run を別 run として事前登録する。または候補範囲を複数条件として比較する。

### B-03 データ分割手順が確定していない

- 人間の判断が必要な項目: 9 組み合わせごとの層化の有無、生成後のサンプル単位分割か生成 seed 単位分割か、分割を決める seed、各組み合わせの端数処理。
- 理由: 80/10/10 という比率だけでは、各 split の構成や再現方法が一意にならない。分割方法は評価結果へ影響するデータセット条件である。
- PROPOSED: 各色×形の 1,000 枚を 800/100/100 に層化し、生成済み `sample_id` に対して固定 seed で一度だけ split を割り当てる。
- 利点: 各 split のクラス構成が一致し、比較が安定する。
- 欠点: 自然に生じる組み合わせ頻度の偏りは評価できず、層化そのものが人工的な制約になる。
- 代替案: 全 9,000 枚を一括で無作為分割する。または、未知の組み合わせへの一般化を別実験として組み合わせ単位で hold-out する。後者は Experiment 001 の目的変更になるため別仕様が必要である。

### B-04 Autoencoder の構造と画像表現が確定していない

- 人間の判断が必要な項目: CNN/MLP 等の構造、層数、チャネル数、活性化、正規化、latent の出力形状、入力値域、decoder の出力活性化。
- 理由: モデルの帰納バイアスと容量は、再構成と潜在構造の形成を大きく左右する。「小規模」だけでは独立実装が一致しない。
- PROPOSED: 単一の基準 architecture を層ごとの入出力 shape まで固定し、パラメータ数を記録する。最初の run では architecture 探索を行わない。
- 利点: 未学習・学習済み比較と seed 間比較の意味が明確になる。
- 欠点: 選んだ architecture 固有の否定結果になる可能性がある。
- 代替案: 事前登録した少数の architecture を別条件として比較する。ただし多重比較と計算量が増える。

### B-05 学習目的と学習手順が確定していない

- 人間の判断が必要な項目: MSE/BCE/L1 の選択、損失の集約方法、optimizer、learning rate、batch size、epoch 数、早期終了の有無、最終モデルか validation-best モデルか。
- 理由: `decisions.md` の MSE は `PROPOSED` かつ未決定である。これらはモデルの学習目的または結果を左右する実験条件であり、Codex が既定値を選べない。
- PROPOSED: 初回 baseline では単一の損失と固定 epoch を事前承認し、解析対象 checkpoint を一意にする。探索をする場合は候補範囲と選択規則を先に固定する。
- 利点: run の比較可能性が上がり、都合のよい checkpoint 選択を防げる。
- 欠点: 不適切な初期設定で学習が失敗する可能性があり、調整には新しい決定が必要になる。
- 代替案: validation loss による早期終了と best checkpoint を採用する。ただし Section 18.3 の `final.pt` との関係を明文化する必要がある。

### B-06 線形プローブの学習・評価方法が確定していない

- 人間の判断が必要な項目: probe の訓練用 split、validation の用途、正則化、ハイパーパラメータ選択、評価指標、probe 用 seed、学習済み Encoder と未学習 Encoder で同一手順を使うか。
- 理由: Section 11/18.5 は Test の latent のみを保存する一方、Section 12 は線形分類器の学習を要求する。Test 上で probe を学習・評価すると汎化性能を測れない。
- PROPOSED: Encoder を固定し、Train latent で probe を学習、Validation latent で設定選択、Test latent は最終評価に一度だけ使用する。
- 利点: データ漏洩を避け、精度を未知サンプルへの読み出し性能として解釈できる。
- 欠点: 全 split の latent 保存またはオンデマンド抽出が必要になり、成果物が増える。
- 代替案: Test latent 内で事前固定の交差検証を行う。ただし Autoencoder の Test と probe の評価集合が混ざり、解釈が複雑になる。

### B-07 距離解析の評価方法が確定していない

- 人間の判断が必要な項目: 距離尺度、latent の標準化の有無、全ペアかサンプリングか、同一サンプル対の除外、seed 間集約、統計的不確実性の扱い。
- 理由: Autoencoder の latent は座標ごとの尺度が一意でなく、尺度変換で再構成を保ったまま距離を変えられる。距離定義は評価方法そのものである。
- PROPOSED: raw Euclidean 距離だけに依存せず、事前に承認した正規化後の距離、効果量、信頼区間を併記する。
- 利点: 単なる latent scale の差を規則的構造と誤認しにくい。
- 欠点: 正規化にも仮定が入り、raw latent の幾何をそのまま測る解析ではなくなる。
- 代替案: cosine 距離、decoder 出力差に基づく距離、または k-NN の近傍組成を主解析にする。いずれも事前承認が必要である。

### B-08 Pixel baseline の必須性と内容が確定していない

- 人間の判断が必要な項目: Pixel baseline を必須にするか、入力表現、モデル、split、評価指標を何にするか。
- 理由: Section 13 は「少なくとも以下と比較する」としながら Pixel baseline を「可能であれば」としている。さらに、成功の解釈には単純な RGB 統計で説明できるかの検討が重要である。
- PROPOSED: Pixel baseline を必須とし、latent probe と同じ Train/Validation/Test 手順の raw-pixel 線形分類を最低限実施する。
- 利点: 潜在表現が入力の単純統計以上の情報を形成したかを比較しやすい。
- 欠点: raw-pixel 線形分類だけでは「単純な統計」の範囲を完全には表せず、位置ずれにも敏感である。
- 代替案: RGB 平均・分散などの明示的統計量、PCA 圧縮 pixels、または複数 baseline を使う。baseline を任意のまま残す場合は、未実施時に結論可能な範囲を狭める必要がある。

## PROPOSALS

以下は仕様改善案であり、すべて **PROPOSED** である。

### P-01 ラベル漏洩をインターフェースとテストで防止する

- 理由: 「使ってはならない」という記述だけでは、同じ batch 辞書に評価ラベルが含まれる実装などの偶発的漏洩を検出しにくい。
- 改善案: 学習用 Dataset/DataLoader は画像と `sample_id` だけを返し、評価メタデータは解析モジュールだけが別ファイルから結合する。自動テストで loss 計算経路に `color`/`shape` が渡らないことを確認する。
- 利点: 研究原則をコード構造で強制でき、監査しやすい。
- 欠点: Dataset 実装と解析実装が分かれ、コード量が少し増える。
- 代替案: 同じレコードを使いつつ学習時にラベル列を明示的に drop し、実行時 assertion を置く。

### P-02 乱数を用途別に記録する

- 理由: 単一の `seed` では、画像生成、split、モデル初期化、DataLoader、probe の乱数を独立に再現・比較できない。
- 改善案: master seed と、そこから決定的に導出した `generation_seed`、`split_seed`、`model_seed`、`loader_seed`、`probe_seed` を保存する。
- 利点: どの乱数要因で結果が変わったかを切り分けられる。
- 欠点: 設定項目が増え、seed 管理が複雑になる。
- 代替案: 全処理に単一 seed を使い、処理順も固定・記録する。ただしモジュール追加で乱数列が変わりやすい。

### P-03 全 split の latent と Encoder 状態を明示する

- 理由: probe の適切な学習には Train/Validation latent が必要で、未学習モデルにも「同じ解析」を行うには初期・最終状態の区別が必要である。
- 改善案: `encoder_state` と `split` 列を持つ単一ファイル、または `latent_vectors/{initial,final}/{train,validation,test}.csv` を成果物として定義する。
- 利点: 解析の入力が完全に残り、probe と未学習比較を再実行できる。
- 欠点: 保存容量とファイル数が増える。
- 代替案: checkpoint と dataset metadata だけを保存し、解析時に latent を毎回再抽出する。再抽出の決定性検証が別途必要になる。

### P-04 未学習・学習済み比較の成果物名を対称にする

- 理由: 現行の PCA、距離、latent の成果物名は学習済みモデル用に一組しかなく、Section 13 の未学習モデルへの「同じ解析」を保存できない。
- 改善案: `analysis/initial/` と `analysis/final/` に同一形式の PCA、距離、probe 結果を保存し、比較要約を別ファイルに置く。
- 利点: 比較対象の取り違えを防ぎ、差分を機械的に集計できる。
- 欠点: 例示された成果物構成から変更される。
- 代替案: 各ファイル名に `_initial` / `_final` suffix を付ける。

### P-05 評価結果に不確実性と基準精度を含める

- 理由: accuracy の一点値と平均距離だけでは、有限サンプルや seed 差を評価できない。
- 改善案: クラス別件数、balanced accuracy、confusion matrix、chance level、seed 間の分布、事前に選んだ信頼区間または効果量を保存する。
- 利点: 「差がある」ことと「差が安定している」ことを区別できる。
- 欠点: 統計手法の選定と説明が必要になり、報告が複雑になる。
- 代替案: 各 seed の raw 指標だけを全件保存し、統計的結論は Experiment 002 へ回す。

### P-06 再構成品質の成果物を定義する

- 理由: `report.md` は再構成結果を要求するが、Test reconstruction loss や入力・出力比較画像の保存先が定義されていない。
- 改善案: Train/Validation/Test の再構成損失と、固定 `sample_id` の `reconstruction_grid.png` を成果物に追加する。
- 利点: 潜在解析を、そもそも再構成を学習できたかと切り分けて解釈できる。
- 欠点: 可視化サンプルの選び方を事前に固定する必要がある。
- 代替案: 数値損失のみを保存する。または全 Test 再構成を保存するが、容量が増える。

### P-07 実行環境とデータ完全性を記録する

- 理由: `git_commit` と設定だけでは、ライブラリ、ハードウェア、決定性設定、生成データの差を追跡できない。
- 改善案: Python/主要ライブラリ/OS/device のバージョン、決定性設定、設定・metadata・checkpoint のハッシュを manifest に保存する。
- 利点: 再現不能時の原因を特定しやすい。
- 欠点: 環境情報が増え、異なる device での完全一致を保証するものではない。
- 代替案: lockfile と `git_commit` のみ保存し、ハッシュは省略する。

### P-08 実行後に設定を書き換えない

- 理由: Section 18.1 の「実験開始後に設定値が変更された場合、実際に使用された値を保存」は、開始時設定の上書きと解釈でき、途中変更の履歴が失われる可能性がある。
- 改善案: 実行開始時に解決済み設定を immutable に保存し、途中変更が必要なら run を失敗として残して新しい run を開始する。実行時派生値は別の manifest に記録する。
- 利点: 実際にどの条件で処理したかが追跡でき、失敗 run も保存される。
- 欠点: 軽微な設定ミスでも run 数が増える。
- 代替案: `config_initial.yaml` と `config_effective.yaml` の両方を保存し、変更履歴をログに残す。

### P-09 解析計画とハイパーパラメータ探索規則を最初の run 前に固定する

- 理由: 結果を見た後に PCA 表示、距離尺度、probe 設定、checkpoint を選ぶと、良く見える結果だけを採用できてしまう。
- 改善案: 主解析・補助解析・探索解析を区別し、主解析の設定と選択規則を `spec.md` に事前登録する。
- 利点: 過大解釈と選択バイアスを抑えられる。
- 欠点: 初回実験で有用な探索が制限される。
- 代替案: Experiment 001 を探索専用にし、得られた仮説を事前登録した Experiment 002 で検証する。

## IMPLEMENTATION_DETAILS

以下は、研究条件が Human によって確定した後であれば、研究条件へ影響しにくく Codex 側で決定可能な事項である。

1. `generate`、`train`、`analyze`、`run` を分離した CLI とモジュール構成にする。
2. 設定ファイルを schema 検証し、未決定の研究条件には暗黙の default を置かず、欠落時に実行を停止する。
3. run directory は新規作成のみ許可し、既存 run の上書きを拒否する。書き込みは一時ファイルからの atomic rename を用いる。
4. CSV は UTF-8、JSON は machine-readable な固定 key、epoch と latent index は 0/1 始まりを文書化して統一する。
5. `sample_id` を全成果物の結合 key とし、重複・欠損・split 重複を検査する。
6. checkpoint loader は architecture/config の不一致を検出し、silent fallback を行わない。
7. 学習コードから評価メタデータへ到達できないこと、同一承認済み設定と seed で metadata が一致すること、split が排他的かつ全件を覆うことを自動テストする。
8. 解析は保存済み checkpoint と metadata だけから再実行可能にし、解析の再実行で Autoencoder の重みを変更しない。
9. 異常終了時も run directory、解決済み設定、エラー情報を残し、失敗 run を削除しない。
10. framework 固有のファイル配置や内部クラス名は Codex が決めてよいが、数式的なモデル構造、前処理、乱数、学習・評価手順は承認済み仕様に従う。

## CONFLICTS

### C-01 Test latent のみの保存と線形プローブ学習が両立しない

- Section 11/18.5 は Test データの latent 保存を指定する。
- Section 12 は latent を入力に線形分類器を学習して性能を測る。
- Test latent だけで学習と評価をすると Test が独立評価集合ではなくなる。Train/Validation latent を使うか、別の probe 用分割規則が必要である。

### C-02 Pixel baseline が必須とも任意とも読める

- Section 13 冒頭は「少なくとも以下と比較する」とする。
- 同節の Pixel baseline は「可能であれば」とする。
- 実装完了条件に Pixel baseline を含めるかが一意に決まらない。

### C-03 「再現可能」が成功条件だが、複数 seed は任意に近い

- Section 14 は「再現可能な規則的構造」を成功条件とする。
- 同節は複数 seed を「望ましい」とするだけで、必須数や判定方法を定めていない。
- 単一 seed では seed を越えた再現可能性を検証できない。

### C-04 未学習モデルに同じ解析を要求するが成果物が一組しかない

- Section 13 は未学習 Encoder に「同じ解析」を要求する。
- Section 18 の `latent_vectors.csv`、PCA、`distance_analysis.csv` は状態を区別する命名・schema になっていない。
- `linear_probe_results.json` だけは initial/final 比較を明示しており、他の解析成果物と非対称である。

### C-05 実行中の設定変更と再現性・失敗 run 保存の境界が不明確

- Section 18.1 は実験開始後の設定変更を許容するように読める。
- Section 15/17/19 は失敗 run の保存と再現性を要求する。
- 途中で研究条件を変更した処理を同一 run とみなすか、新しい run とみなすかが決まっていない。

## PLAN

現在の `spec.md` を変更せずに進める場合でも、AGENTS.md のワークフローに従い、**B-01〜B-08 が Human により決定され `spec.md` に反映されるまでは IMPLEMENT/RUN へ進まない**。提案だけを根拠に既定値を選ばない。

決定後の実装計画は以下とする。

1. **DECISION gate**: 各 BLOCKER の決定が `spec.md` に存在し、`decisions.md` と矛盾しないことを確認する。
2. **設定と成果物 schema**: 承認済み条件を表す config schema、run directory、manifest、上書き防止を実装する。
3. **データ生成**: 9 組み合わせを承認済み分布で生成し、metadata と split を保存する。画像と metadata の整合性を検証する。
4. **モデルと学習**: 承認済み Autoencoder、前処理、損失、optimizer、停止規則を実装する。学習前 checkpoint を保存してから訓練し、ログと最終 checkpoint を保存する。
5. **潜在抽出**: 承認済み split と initial/final Encoder について latent を抽出し、`sample_id` で評価 metadata と結合する。
6. **解析**: 同一の承認済み手順で PCA、距離解析、線形プローブ、未学習モデル、Pixel baseline を実行する。Autoencoder へ解析勾配を返さない。
7. **VERIFY**: label leakage、再生成、split 排他性、checkpoint round-trip、成果物 schema、既存 run 非上書きを自動テストする。小規模 smoke run は本実験 run と分離して保存する。
8. **RUN**: 承認済み seed と条件を変更せずに実行し、成功・失敗を問わず全 run を保存する。
9. **ANALYZE**: 数値的な観測事実と科学的解釈を分けた `report.md` を作成する。成功条件の判定と解釈は Human の確認対象とする。

現仕様のまま今すぐ可能なのは、研究条件に値を与えない CLI/config schema、上書き防止、成果物 writer などの非研究的 scaffolding までである。ただし、それらも正式な DECISION の後に着手するのが AGENTS.md の定める順序に最も整合する。
